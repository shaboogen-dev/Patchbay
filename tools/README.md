# Tools

The tools work in a **workspace**: one folder holding the repositories side by side (`BML/`, `Mods/`, and optionally `Mapper/` and `Internal/`), Bitwig's jars (`bitwig/jars/<version>/`) and the generated test installs (`testing/installs/`). `workspace.py` finds each part: the workspace is BML's parent folder (or `BML_WORKSPACE`), and an optional, untracked `workspace.json` at its root overrides any folder (keys and defaults in `workspace.py`). Without `Mapper/`, map packs come from `maps/<version>/` (e.g. from a downloaded release); without `Internal/`, results go to `testing/results/`. Mods are found by ID in `BML/frameworks/` (the frameworks) and `Mods/`.

| Script | Use |
|---|---|
| `build_mod.py <mod-id> [--check \| --replace]` | Build `<mod folder>/releases/<id>-<version>.zip` from the mod's `src/`, `mod.json`, `build.json` and `package/` (layout in `Mods/README.md`). `--check` builds in a temp folder and compares with the existing ZIP of that version. It passes when every class is byte-exact or has the same instructions member by member (line numbers, constant-pool indexes, lambda numbering, member order, stack-map frame types and class-attribute order may differ, and the last two are listed) and the class versions, jar resources and shipped files match. `--out DIR` writes the ZIP elsewhere for testing. Refuses without source. A mod with `"kit": true` in `build.json` is built with the mod kit (`modkit/README.md`): compiled against the kit's compile jar, finished by `modkit finish`, and its shipped `mod.json` generated. |
| `bml_build.py suite <build> [--out DIR] [--replace] [--loader ZIP] [--map ZIP] [--mods ID,ID] [--add-mods DIR] [--skip ID=REASON]` | Build `testing/installs/<build>/` (or `--out`) from the current loader, the map pack in `Mapper/maps/<build>/` (or `maps/<build>/`) and the accepted mods (`--mods`: only these). A build is named as the mapper names it: `6.1.4` is Windows, `linux-6.1.4` Linux (Bitwig in `/opt/bitwig-studio`; its packs are in `maps/linux-6.1.4/`), `macos-6.1.4` macOS (Bitwig in `/Applications/Bitwig Studio.app`; packs in `maps/macos-6.1.4/`; the loader must carry the Mac-built agent). A macOS install is also packed as `testing/installs/<name>.zip` (`.sh` files executable) to copy to the Mac, where `sh bml-ui.sh`, run once from Terminal, first clears the quarantine macOS gives the unpacked files; after that the tester double-clicks `BML.command` in the install folder (only macOS installs carry it; the ZIP gives it and the `.sh` files mode 0755). A newly downloaded install is quarantined again and needs the Terminal line once more. Test-only components come from the mod's `test-components/` and from `Internal/test-components/<mod-id>/`: a ZIP is unpacked, any other file or folder (a panel's `.json`, a theme's `.bte`) is copied as it is, and `test-components/selection.properties` is the saved choice. Then run `guard_selective.py --prepare` in a Windows install, or `sh loader/prepare-mod.sh /opt/bitwig-studio/bin mods` in a Linux one under Linux; a macOS one prepares on the Mac at Load. |
| `bml_build.py clear <name> --note "..."` | After the user's test of `testing/installs/<name>` passes: copy its sessions, BUILD-INFO and offline summary to `Internal/testing/results/<name>/` (without Internal, `testing/results/<name>/`) with a `RESULT.json`, then delete the install (and a macOS install's `.zip`) (standard 2). |
| `bml_build.py release [--platform windows\|linux\|macos\|all] [--mods [PLATFORM=]a,b] [--loader ZIP] [--out DIR]` | Build the tester release per platform in `dist/` (or `--out`): `BML-<loader>-windows.zip`, `BML-<loader>-linux.zip`, `BML-<loader>-macos.zip` (`--platform`: only one; default `all`) and `BML-<loader>-workspace-maps.zip` (below). `--loader` uses another loader core ZIP than the **Current.** one. `--mods a,b`: only these accepted mods on every platform built; `--mods linux=a,b`: only on that platform (repeatable). |
| `porter/SourcePorter.java` | Port Java source between Bitwig versions: `java tools/porter/SourcePorter.java --cp <from jars> --map <remap.tsv.gz> [--invert] --src <dir> --out <dir>`. Uses javac to resolve every symbol and renames only mapped Bitwig classes/members (also imports, overrides, method refs, class-name strings and unambiguous reflection). Flags other suspicious strings for review. |
| `method_diff.py <want.class> <got.class>` | Per-method `javap` diff with constant-pool indexes stripped; `build_mod.py --check` uses it to compare classes. |
| `mod_uses.py` | Lists the Bitwig classes and members a `helper.jar` uses (`uses.tsv`) and checks them against a map pack. A member is attributed to the Bitwig class or interface that declares it, searching the superinterfaces even when the superclass chain leaves bitwig.jar; only one no Bitwig type declares is the JDK's (`-`) and goes unchecked. |
| `workspace.py` | Where the workspace's parts are (above). |
| `guard_selective.py` | Copied into each suite; checks the installed Bitwig hash, runs offline prepare (refused without the marker below); `--ready` says whether the install is ready to open with `bml-ui.cmd`. |

Inputs it reads: the **Current.** row in `loader/README.md`, the single ZIP in each `Mapper/maps/<version>/` (or `maps/<version>/`), and the **Accepted** column in `Mods/README.md` (one table for the frameworks and the mods).

Every suite has the marker `config/portable`: it keeps its settings in `config/` and `state/`, so a test never touches the user's per-user settings folder and `clear` removes them. A release doesn't have it. A loader smoke test that runs a real `bml-control.jar` in a scratch install must write that marker first.

`suite --add-unticked DIR` also installs the mod folders in `DIR` as they are, unticked (for example a mod not available on that build, to see how the window shows it); the offline prepare (`guard_selective.py --prepare`) prepares only the ticked mods, as Load does.

A mod goes into a suite only if the map pack holds a remap from the mod's `built_against` build (version and platform: a mod written against Windows 6.1.4 needs `remap/windows-6.1.4__<target key>.tsv.gz`, one written against macOS 6.1.3 `remap/macos-6.1.3__<target key>.tsv.gz`) and that remap translates every row of its `uses.tsv` (generated from `helper.jar` against the build's jar when the mod has none). Skipped mods are listed in the suite's `BUILD-INFO.json`.

## Release

`BML-<loader>-<platform>.zip` (`windows`, `linux`, `macos`) holds one folder, `BML-<loader>-<platform>/`, that is a working install for that platform as unpacked:

- the loader core (the **Current.** row in `loader/README.md`, or `--loader`) with only that platform's files (`core_platforms` in `bml_build.py`): on Windows the DLL agent and the `.cmd`/`.ps1` scripts; on Linux the `.so` agent and the `.sh` scripts; on macOS the `.dylib` agent, the `.sh` scripts and `BML.command`. The agent's platform build inputs go with their platform (`include/linux/`, `include/darwin/`, `build-agent-mac.sh` and the dylib's record); every other core file ships on every platform. `INSTALL.md` (from `tools/release/INSTALL-<platform>.md`: the tester's install steps, with the folder name, loader version and Bitwig versions filled in) replaces the core's `README.md`;
- the platform's map packs, unpacked into `maps/`: every `<maps>/<version>/` for Windows, every `<maps>/linux-<version>/` for Linux, every `<maps>/macos-<version>/` for macOS;
- every mod in the Accepted column of `Mods/README.md`, the frameworks included, each with its `src/`. No components (so no theme) and no saved selections: the window starts with its defaults (manifest v2 mods ticked; Framework: Themes, a v3 mod, unticked and unavailable until a theme is dropped in `components/`);
- `modkit/` (`bml-api.jar` and `bml-modkit.jar`, built from source by `modkit/build.py`, and `modkit/README.md`) and `docs/` (the guide), so a tester can build mods without the repository. In the guide's build steps `$Kit` is `<install>\modkit`, framework jars are `<install>\mods\<framework-id>\helper.jar`, and the offline check is `<install>\loader\prepare-mod.cmd` (`<install>/loader/prepare-mod.sh` on Linux and macOS).

The Linux and macOS ZIPs are marked as made on Unix, with `.sh` and `.command` files mode 0755; the build refuses a shell script with CR line ends.

`BML-<loader>-workspace-maps.zip` holds every platform's map pack ZIPs as `maps/<build>/<pack>.zip` (`maps/6.1.4/`, `maps/linux-6.1.4/`, `maps/macos-6.1.4/`, ...), whichever `--platform` is built. Unpacked into a workspace (a clone of BML without `Mapper/`), they are the build tools' `maps/` fallback.

No mod is chosen per Bitwig version. From loader 0.34.0-dev.18 the preparer leaves out a mod the installed Bitwig's map can't translate (made for a version the map has no remap from; standard 13), lists it after `PREPARE_OK`, and the window shows it as not available on that version. A map that has a remap but can't translate every name a mod uses would stop preparation instead, so the build refuses a mod whose `uses.tsv` any map in that platform's ZIP can't fully translate. The build also refuses a mod without `src/` (standard 9), a `components/` or `state/` folder in the release, and a kit `bml-api.jar` that differs from the loader's. ZIP entries are sorted with fixed times: the same inputs give byte-identical ZIPs.

Offline check of a release (never in `testing/installs/`): unpack it to a scratch folder and run `loader\prepare-mod.cmd <Bitwig bin> <install>\mods` (Windows) or, under Linux, `sh loader/prepare-mod.sh /opt/bitwig-studio/bin <install>/mods`. To prepare what the window's Load would, set `BML_MOD_SELECTION_ACTIVE=1` and `BML_ENABLED_MODS_FILE` to a file listing the ticked mod IDs, one per line; without them every folder in `mods\` is prepared, and Framework: Themes refuses without a theme.
