# BML Loader

| Path | What |
|---|---|
| `src/` | The one loader source tree: control app (`loader/app/src`: the Patchbay window, the preparer; `loader/app/resources`: files copied into the jar), JVMTI tracer source, preparer scripts, schemas, tests, map tools, launchers. |
| `build.py` | `python loader/build.py` → `releases/BML-<version>-core.zip`. Compiles the control app (JDK 25, `--release 21`; `DarkTitleBar.java` alone at `--release 22`, listed in `APP_RELEASE_OVERRIDES`), copies `loader/app/resources` into its jar (the bundled fonts when present; without them it warns and the window uses the platform's fonts), refuses a jar that needs a module Bitwig's Java runtime lacks (`jdeps` against `BITWIG_RUNTIME_MODULES`; today `java.base,java.desktop`), and the eight classfile tools in `src/loader/tools/src` (JDK 25, `--release 21`) and the native JVMTI tracer from source: `loader/jvmti/bin/bitwig-jvmti-tracer.dll` for Windows (MSVC, VS Build Tools 2026) and `bitwig-jvmti-tracer.so` beside it for Linux x86-64 (g++ 13.3.0 from Ubuntu 24.04 `build-essential`, run in WSL `Ubuntu-24.04`; the build refuses any other g++). The macOS agent `bitwig-jvmti-tracer.dylib` (universal arm64 + x86_64) can only be built on a Mac: `python loader/build.py --mac-kit DIR` packs the kit (agent source, `build-agent-mac.sh`, headers), the Mac builds it with the pinned Xcode command-line tools (26.6, Apple clang 21.0.0, SDK 26.5), and `src/loader/jvmti/bitwig-jvmti-tracer.dylib.sha256` records the toolchain and the SHA-256 of every input and of the result. The build takes the Mac-built file from `mac-input/bitwig-jvmti-tracer.dylib` (ignored by git) or `--mac-dylib PATH` only if the recorded inputs are still the source's and its SHA-256 is the recorded one, and refuses a release without it; `--no-mac` builds `releases/BML-<version>-core-no-mac.zip`, a development build without macOS support. Nothing prebuilt is taken from `src/`. Reproducible: same source, same ZIP. |

## The window (Patchbay)

`bml-ui.cmd` / `bml-ui.sh` (and `BML.command` on macOS) open it; the name it shows is `AppText.NAME`. Folders, jars, scripts and IDs keep the name `bml`.

- **Pages:** Mods, Maps (with **Library**), Errors, Sessions, Settings (with **System**), each with a count beside it except Settings. Selecting a row (click, or Enter on the highlighted row) shows the teal **selection bar** with that item's options above the error strip; Esc clears it. Only tick boxes tick. Long text (a mod's README, a session's log) opens in the full-window **reader**: text-only Markdown (links ask "Open this link?", images left out), or the log, live and following while the session runs.
- **Mods:** tick, name (area muted), description (with a status note only when it adds something: not available, needs a mod, can't load, a device folder missing, a component to choose), version, author; ordered by area (ignoring case) then name. Search, Show (All / Ticked / Unticked / Disabled; remembered as `ui.mods.show`), Select All / Deselect All, Refresh; mods, components and maps are read again whenever the window regains focus. The bar: component choice (a dropdown for a single choice, tick boxes for several) and Components Folder, Device folders… (on Framework: Nitro Devices), README, Open on the Web (when the manifest gives `homepage`), Open Folder, Disable Mod / Enable Mod, and the ID, folder, needs and issue count. A mod's right-click menu (also Shift+F10 or the menu key) has README, Open on the Web, Open Folder and Disable Mod / Enable Mod. **Disable Mod** sets a mod aside without uninstalling it: it leaves the list, is never prepared or loaded, and its issues (and those of components made for it) don't show on Errors or block Load. Show > Disabled lists only the disabled mods, dimmed with a greyed tick box, with Enable Mod; the other Show choices leave them out; enabled again, a mod is unticked. A mod a ticked mod needs (directly or through another) can't be disabled: the entry is greyed with the reason. Ticking a mod whose prerequisite is disabled enables and ticks the prerequisite, and the status line says so. The IDs are kept as `mods.disabled` in `bml.properties` (an ID that isn't installed is kept and ignored).
- **Errors:** blocking first, then warnings, then info; the bar has the problem, fix, code and path, and Open Location (or Device folders… / Remove Folder for a device folder, Open Settings when Bitwig isn't found). Session folders found broken at start-up are warnings here.
- **Sessions:** newest first; the bar has status, how long Bitwig ran (recorded as `ran_ms` in `session.json` when the window sees Bitwig exit), mode, mods, PID and ID, with View Log, Open Folder, ZIP Session, Delete Session. Clear All; completed sessions older than 7 days are offered for clearing in a notice at the top (Keep for Now hides it for 7 days).
- **Maps:** the status card (Import Map…, Open Folder), one line per map, and the explanation.
- **Settings:** Bitwig Studio (Browse… saves at once), Show Debug Mode (off by default; reveals the footer's Debug Mode box), the settings folder (Open Folder, Delete), About (the Bitwig versions the installed maps support, Open on GitHub), Acknowledgements.
- **Footer:** the status line, preparation progress, View Live Log while Bitwig runs, Debug Mode (when shown), Stop / Quit and Load. While an error blocks Load, Load is greyed and a red strip names the first error with **Show in Errors**. Dialogs only for what must be read: Load refused, a failed delete, Bitwig failing to start, and confirmations.
- **Look:** OS title bar, dark (Windows: `DwmSetWindowAttribute` through `DarkTitleBar`; macOS: the dark appearance; Linux follows the desktop; any failure leaves the normal bar), the socket-and-cable mark as window and Dock icon, Outfit and JetBrains Mono when bundled, no motion, no tooltips. `bitwig.jar` is hashed in the background, so the window opens at once.

**Which Java runs it** (`loader/find-java.cmd` on Windows, `bml_find_java` in `loader/platform.sh` elsewhere; the window passes its own Java to the preparer as `BML_JAVA`): `BML_JAVA`; the runtime of the Bitwig being prepared for (preparation only); the Bitwig chosen in Settings; the Bitwig in its default place; `JAVA_HOME`; `PATH` (and `/usr/libexec/java_home` on macOS). A Bitwig runtime counts only when its `release` file lists `java.desktop`; `JAVA_HOME` and `PATH` only when they are Java 21 or later. Windows starts the window with `javaw.exe` (no console window); macOS adds `-Xdock:name=Patchbay`; every platform passes `--enable-native-access=ALL-UNNAMED` for the title bar.

The version comes from `LOADER_VERSION` in `src/loader/app/src/dev/bitwigre/bml/JavaPreparer.java`. The previous design (v1 maps, 0.32.0 Modular) is kept as one representative in `archive/`.

The tool smoke tests in `src/loader/tests/` run against a built loader: unzip a release and set `BML_LOADER_ROOT` to its `loader/` folder (the jars are build outputs, not in `src/`). Only `smoke_helper_inherited_owner_calls.py` and `smoke_bitwig_owned_inherited_calls.py` are updated for that and for Windows so far.
